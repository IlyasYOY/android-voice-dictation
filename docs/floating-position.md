# VD007 — remembered floating circle position

The default remains the circle at the right, 8dp above the keyboard. A completed user drag stores one versioned private preference in the existing `floating` namespace. It contains only the horizontal fraction of safe circle travel (0 at the left, 1 at the right) and the gap in dp between the circle's bottom and the safe bottom above the keyboard. No editor identity, field text, screen contents or microphone state is stored with it.

Horizontal fraction adapts to display width; the dp gap preserves the user's chosen distance above keyboards of different heights and displays of different densities. System bars/cutouts and an 8dp side/bottom margin bound the available area; the existing 24dp top fallback remains when no larger top inset is reported. The circle is hidden if a full 64dp touch target cannot fit. Android 30+ uses maximum window metrics/insets; older Android uses real display metrics and attached window insets. The same pure geometry is tested with asymmetric cutouts, navigation bars and cramped orientations.

The anchor belongs to the circle, not to its wider temporary controls. An expanded menu can temporarily shift the window so all controls fit. Rotation, keyboard height changes, inset dispatch, visibility polling, hide/show and temporary clamping only project the saved anchor into reachable bounds. They never overwrite it. Returning to the previous geometry restores the preferred location. The on-screen window is clamped during motion; only a completed drag release commits a new preference. A tap, long press, cancelled gesture or hiding midway through a gesture does not save a position or start a dictation accidentally.

A drag changes only axes with deliberate motion beyond touch slop (a short diagonal beyond the combined slop changes both). Thus a horizontal drag while the keyboard temporarily clamps the vertical position keeps the prior preferred gap, and a vertical drag in a cramped width keeps the prior horizontal intent. Finger jitter on the unchanged axis does not turn a temporary layout constraint into a new preference.

The small preference is committed synchronously once on drag release, so a successful save survives window/service/process recreation and device restart. It is loaded when a new window is created; no boot receiver or automatic microphone/network work is added. A write failure keeps the current window's placement in memory, but durability is not claimed. Missing preferences, unsupported versions, wrong legacy preference types and non-finite/invalid numbers safely fall back to the default without rewriting unrelated settings. Finite large gaps are clamped for display rather than overflowing pixel coordinates.

Validation and actual screenshots are kept outside Git. Unit tests cover persisted round trips, geometry/keyboard/density changes, temporary clamping, invalid inputs and failed writes. Android tests check real preference commits and non-mutation during geometry changes. A separate-UID fixture scenario exercises actual drag, keyboard hide/reopen, Home, rotation and an explicit service disable/process restart/re-enable through the existing Android consent UI. Execution results and emulator limitations must be reported separately from test compilation. No video or release is part of this step.
