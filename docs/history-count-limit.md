# VD009 history count limit

The default is 100 items. Settings accepts a positive whole count (1 through the platform integer range, 2,147,483,647); input is rejected rather than clamped. An atomic, synced private `history-limit.properties` setting survives process death and app updates. An older install with no setting uses 100 without deleting or rewriting any recording. Lowering below current use is allowed and keeps every item; subsequent new starts wait until the user deletes enough items or raises the limit.

One ledger row counts as one item in every status: capturing, pending, failed, interrupted, complete, unavailable or explicitly deleting. One Record dictation is one item including its audio and transcript. One Live session is one text-only item, updated by successive transcript checkpoints; it never creates one item per partial/turn. Active Live without a first text checkpoint temporarily reserves one place. The main compact saved count still counts actual saved rows; the capacity usage includes these active admissions too.

Main and AccessibilityService run in the same application process and share the single `AndroidRecordingStorage` repository. Its synchronized admission/setting operations serialize competing starts. Record admission is the durable CAPTURING row allocated before MediaRecorder creation/start. Live takes an in-memory admission before connecting or starting PCM, and holds it until the final checkpoint. Cancelling an empty Live releases an admission, not a saved recording. On process death, no old microphone owner remains; empty Live admissions vanish, while every checkpointed Live row and interrupted Record row is restored and counted. Explicit Cancel retains its existing owned-capture semantics.

The limit governs admission, never preservation. An already admitted capture may finish after the limit is lowered. Legacy import, recovery of already stopped audio and safety checkpoints of already received Live text may temporarily put existing data above the chosen count. Those data stay intact and block subsequent starts. Existing retry, playback, transcript expansion/edit/copy and explicit confirmed Delete do not require a free place. No automatic upload/retry/eviction or background cleanup of saved items is added.

At capacity, main shows a neutral History full surface with History and Limit actions. The ordinary recording control is disabled, while existing-item actions remain available. The shared sheet provides the same setting when full. The floating affordance announces History full and opens the shared history only on an explicit tap/hold, before starting a foreground microphone request; visibility polling never opens a popup. It keeps passive results, never carries an editor token through settings, and the next recording tap rechecks the current editor/selection. A last-place race is also rejected by the session/recorder gate without microphone or HTTP use.

Unknown/unreadable setting data does not make history inaccessible or silently disable the limit: new starts fail closed with the existing generic storage error, existing-item operations remain possible, and an explicit valid settings save repairs the count setting. Setting-write failure retains the previous committed value. Incomplete recording allocation remains counted as unavailable data for explicit cleanup instead of permitting repeated capacity bypass.

Machine/runtime reports and actual screenshots remain outside Git. Validation uses synthetic local audio/text and localhost responses, never a paid API credential or reference-message content. A new Draft PR is for user acceptance; no merge or release is part of VD009 authorization.
